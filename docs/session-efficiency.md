# 续接效率与可读询问

2026-10-21 对本机近期的 Bridge 请求做只读审计：一次手动排查会话中约六分之一的请求重新发送了全部历史，这些重建累计重复发送了数十万字符的相同工具结果。旧日志没有前缀差异诊断，不能把这些重建都归咎于同一个原因，也不能把历史重写、压缩或切换模型的必要重建算作可安全删除的重复。

## 本次修复

- 首次模型请求带完整协议；同一 Qoder 会话的后续增量只带简短续接说明，继续遵守已有协议。工具选择始终显式保留；工具 schema 改动仍完整发送，未改动的 schema 不重复压缩或发送。
- Host 回传的第一条 assistant 工具调用如果与刚刚校验通过的决策逐个同名、参数对象完全相同、批次数相同，且没有其它内容或未知字段，只发送新分配的工具 ID、名称和参数哈希；完整参数已存在于同一模型会话。仅在这样确实更短时去重。后续真实工具结果原样保留，参数改动、其它调用或新会话都不适用。
- 会话前缀按实际发送给决策模型的消息表示比较。不把未发送的 reasoning/本地传输元数据变化当作历史改写；角色、正文、工具 ID、工具参数或命名变化仍会使前缀不匹配。不会用忽略真实历史变化的方式强行复用。
- `context_transport.optimization` 记录协议复用与省去的参数字符数。`context_transport.reset` 记录历史缩短/改写、首个变化位置、角色、数量和 SHA-256，不复制正文。Bridge 重启、会话淘汰或真正历史改写仍可能需要重新发送完整上下文。

这减少传输和累计模型上下文，不承诺真实推理时长或账号费用按同一比例降低。缓存仍按既有来源标记；SDK 报告 Credits=0 不证明账户没有计费。未改用户选择的模型、窗口和 effort；未扩大推理守卫、纠错次数或期限。

## 不把工具协议显示为回答

实际日志中出现过畸形的 `<system_call><name=...>` 原始回复，旧版误判为纯文本 final。现在识别这种协议意图并拒绝整批，进入原有最多两次的请求内纠正；不能猜补参数或执行半批。即使模型把这段坏输出包装进 final.content，也不会先流给 DSH。

需要用户选择时，使用 DSH 声明的 `ask_user_question` schema，或给出自然语言回复。JSON 字符串中的一般 XML 示例与文件工具参数仍作为数据保留。离线验证使用了本机记录的坏输出、DSH 问题 schema 和本机 pi-ai 适配器；仓库测试只含合成样例。模拟重生成通过不等于真实上游模型恢复率。

## 边界

本次修复只涉及 Bridge 自身的上下文传输与决策解码。DSH 中其他模型提供商的上游拒绝（例如渠道校验未通过）不在 Bridge 范围内，Bridge 不能解除，需要按服务方支持的接入方式处理。

审计报告保存在本机 `reports/`，不进入仓库。
