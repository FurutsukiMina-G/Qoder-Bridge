# 请求内决策恢复

Bridge 默认在**同一个 HTTP 请求、同一个 Qoder 会话、同一把会话锁和原总期限内**处理模型工具格式错误。Harness 仍拥有全部真实工具和权限审批；Bridge 的 SDK 会话仍为 `tools: []`、`maxTurns: 1`，没有扩大执行权限、上下文或输出预算。

## 原因与改动

当前接入路径把 Harness 的工具 schema 和对话交给 Qoder，再从模型的文本输出解码工具决策。这不是有语法约束的原生 Function Calling。JSON 提示词不能保证模型不会生成 DSML、混合包装、缺字段或类型错误。

旧流程会在校验失败后直接结束 HTTP 请求，仅给会话保存 `retryHint`。只有外部再次提交请求，模型才能看到纠错提示。不断补解析分支可以处理完整、无歧义的历史变体，不能补出缺失的 `new_string`、猜位置数组或执行截断命令，因此不能消除外部续跑依赖。

新流程为：

1. 在调用模型前检查工具名唯一性、JSON schema 和指定工具是否可用。配置错误以 HTTP 400 返回，不消耗模型纠正次数。
2. 正常生成并完整校验决策。工具名称、`tool_choice` 和每个调用的 schema 都必须通过；拒绝的批次不会发送任何一个工具。
3. 若上游正常结束、输出非空但格式/参数不合格，向同一个模型会话发送短的纠错消息，包含实际校验错误、允许的名称和相关完整 schema。明确指出被拒绝的工具没有执行。模型重新生成完整决策，Bridge 不改写命令或补参数，也不重发全量历史。
4. 默认最多额外纠正两次；连续收到相同坏输出提前停止。已经向客户端发送了正文的回答不撤回重写。预算耗尽、认证/额度/权限/SDK 故障、空输出、取消和超时不会触发格式重试。
5. 耗尽后返回 `model_decision_recovery_exhausted`。同一保留会话内再次收到完全相同的失败请求，直接返回已记录失败，不再启动付费循环。新用户消息、schema 或请求参数变化可开始新的决策。此断路状态属于当前进程和会话，未启用跨进程 SDK 恢复。

相同成功请求的本地重放保留原工具调用 ID，避免网络重试把同一个已生成调用包装成新调用。该机制在现有短时成功重放窗口内生效，不替代 Harness 的工具执行去重和会话状态。

SDK 明确报告每日额度、计费/额度、认证或限流错误时，HTTP/SSE 直接给出对应的 `upstream_daily_limit`、`upstream_billing_error`、`upstream_authentication_failed` 或 `upstream_rate_limit` 及安全的固定说明，不再只显示泛化的 Bridge 错误。识别仅依据 SDK 失败元数据，不读取模型正文或工具输出，不追加自动重试，也不猜额度恢复时间。

DSH 中可见的来源标签、SDK 原始错误码、请求 ID 及无法定位的边界见[中断错误诊断](error-diagnostics.md)。

参数 `--decision-retries 0|1|2` 可设置纠正次数，默认 `2`。`0` 用于排查时关闭内部纠正；SDK 自己的单轮限制保持不变。总请求期限包含排队、首次生成和所有纠正，不因纠正重新计时。

## 观察与用量

- `/health` 显示 `capabilities.decisionRecovery`，各模型池的 `decision_recovery` 给出恢复数和耗尽数。正常模型/工具请求不需要外部 agent 逐条监控或续跑。
- `reports/bridge.ndjson` 的 `decision_recovery.evidence` 保留每次尝试的原始正文、响应哈希、校验错误、终止原因、用量来源和 Credits。只记录原始输出正文，不保存私人推理全文。
- `reports/tasks.ndjson` 只保留摘要、次数、失败原因与响应哈希，不再复制完整坏输出。历史原始报告保持可读。
- 一次 HTTP 请求可包含多次模型调用。`model_requests` 与 Bridge 请求数分别记录；旧日志缺少上游调用计数时标为未知，不把每个历史 HTTP 请求猜成精确的一次调用。
- Credits 和可用的 token 用量包含所有尝试。任何尝试用量未知时，总量仍未知，同时单列已知 Credits 小计，避免当成零或重复相加。token/缓存的既有来源标记保持，推导值不会变成上游精确计量。聚合请求不使用最后一次的解码速率冒充整轮速率。
- 多次尝试时，日志的 `normalized_usage` 是全部尝试的累计消耗；发给 Harness 的 usage 是**最后一次尝试的输入 + 全部尝试的输出**。Harness 把最近一次调用的 usage 当作当前上下文长度，累计输入会让它误以为上下文翻倍而提前压缩。
- 推理守卫中断的尝试（`stage=reasoning_guard`）同样占用纠正次数，重试从 `max` 降为 `high`；全部耗尽返回 `qoder_reasoning_budget` 并断路相同请求。见[推理守卫](billing-and-reasoning.md#推理守卫)。
- 工具 schema 按内容缓存并限制容量；独立客户端的 `$id` 命名空间分离，避免跨任务校验污染和每个 HTTP schema 副本无限滞留。

只读检查可用 `Invoke-RestMethod http://127.0.0.1:8646/health` 和 `npm.cmd run metrics -- --session <原会话ID> --limit 10000`。`knownCredits` 包含有部分未知尝试时仍可确认的小计；同时查看 `unknownCreditRequests`。失败断路后应检查错误与原始证据，不用重启服务或反复提交同一请求来清空限额。

## 验证及边界

2026-10-19 以一次实际长任务的日志为基线：约 3% 的 Bridge 请求失败，其中绝大多数是格式/参数错误，另有一次输出预算耗尽和一次客户端断开。在现有真实 Harness schema 下，约三分之一的历史格式失败已能直接解析，其余格式失败在原始失败输出加确定性模拟模型重生成的离线回放中全部恢复；非格式失败没有重试。报告保存在本机 `reports/bridge-reliability-{baseline,replay}-20261019.json`，不进入仓库。

离线回放证明状态机、校验和安全边界，不代表真实上游模型的长期恢复率。自动测试还覆盖并发同会话、整批原子交付、相同请求断路与工具 ID、提前正文、取消/SDK/预算错误、schema 预检和部分未知计量。测试不执行 Harness 的应用工具。

Bridge 不代替用户批准权限，不解除额度限制，也不判断应用项目的业务交付是否完成。有效最终答复、真实工具执行错误、系统交互和物理设备验收仍由 Harness/用户处理。内部纠正耗尽、用户主动停止、额度或审批问题需要明确处理条件，不能再由外部监控无限添加续跑提示。业务交付审计可以继续，但不再是格式纠错的运行依赖。
