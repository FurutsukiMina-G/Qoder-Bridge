# 计费反推缓存、推理守卫与 Harness 内调节

## 缓存统计：由每个请求的 Credits 反推

Qoder 不返回缓存字段，但每个请求都报告 Credits。用本机实际长任务日志拟合（输入、输出 token 均已逐请求精确计量）得到：

- **Credits = 22.22 × DeepSeek 官方人民币标价**。官方空闲价（元/百万 token）：Flash 未命中输入 1、缓存命中 0.02、输出 4；V4 Pro 为 4.5 / 0.15 / 13.5；高峰时段价格翻倍。
- **高峰时段**：北京时间周一至周五 9:00–12:00、14:00–18:00（不含法定节假日）；其余时间、周末和节假日为空闲价。
- **校准精度**：以续接请求（上一请求恰为本请求前缀）为基准稳健拟合，K = 22.22、单请求固定开销约为 0；续接请求中位误差 0.47%，93% 在 5% 以内。由账单反推的命中数与前缀估算的中位差为 −7 token。以输出为主的请求单独估得的 K 也稳定在 ±0.5% 内。
- **Pro 同样吻合**：新会话首请求按全部未命中计价时与账单相差约 3 token；续接请求的命中数比上一请求输入少 64–80 token，符合 64 token 的缓存块粒度。这也印证了 Pro 的输入、输出计量。

输入 P 与输出 O 已知后，账单里唯一的未知量是缓存命中 H，可逐请求解出：

```text
H = (未命中价 × P + 输出价 × O − Credits × 10^6 / (K × 时段倍率)) / (未命中价 − 命中价)
```

serve 默认 `--cache-usage billing`：把反推的 `cached_tokens` 发给 Harness，日志 `cache_billing` 记录命中/未命中、实际时段与日历时段。解出的 H 超出 [0, P] ±1% 时视为价目已不能解释账单，回退到会话前缀估算，并在 `client_cache_usage` 标明来源。`estimate`（总用前缀估算）与 `none`（不发送）保留。

日历按官方规则判定时段；若高峰时段的续接请求明确按空闲价计费（节假日），或周末按高峰价计费（调休），记为当日例外（`/health` 的 `billing_calendar_overrides`），进程重启后清空。

这是由账单推得的数值，不是 Qoder 报告的字段。官方价目、Qoder 的换算或节假日规则变化都会使反推失效；超范围时 bridge 自动回退，需要按新数据重新校准 `src/billing.ts`。

两个此前看不到的现象：

- 新 Qoder 会话的首个请求常有大量**跨会话命中**（Harness 系统提示和工具定义相同），前缀估算会把它当作完全未命中。
- 切换推理等级或上下文窗口后，首个请求可能整体未命中，此后恢复。

## 额度主要花在哪里

按账单反推拆分本机实际长任务的消耗（相对比例）：

| 部分 | 占比 |
|---|---:|
| 推理输出 | 约 37% |
| 未命中输入（每步新增内容与工具结果） | 约 32% |
| 命中输入（每步重复读取已缓存的上下文） | 约 19% |
| 正文输出（决策与回答） | 约 11% |

- 输入整体命中率约 96.5%，命中部分单价只有未命中的 1/50，但上下文越长，每步重复读取的命中输入就越多。
- 高峰时段的请求约占花费的 44%。同样的任务在空闲时段运行约省一半。
- 推理高度集中：推理最多的 5% 请求占全部推理 token 的 46%。部分请求用 2–3 万推理 token 只决定读取几个文件。
- 失败请求直接花费约 2%。其中输出预算耗尽（推理到上限且没有正文）单次花费数 Credits，并会中断长任务。

## 推理守卫

`--reasoning-guard-tokens`（默认 24000，约为实际分布的 p99；0 关闭）：单次尝试在产生任何正文之前推理达到该值时，bridge 用 SDK 的 `Query.interrupt()` 中断该轮，在同一 Qoder 会话里以较短提示重试，要求只决定下一步、信息不足时先读取或搜索，不重发历史。

- 重试与格式纠错都从 `max` 降为 `high`；用户选的 `low`/`high` 保持不变。
- 守卫重试和格式纠错共用 `--decision-retries` 次数。全部耗尽时返回 `qoder_reasoning_budget`，不派发任何工具；完全相同的 HTTP 重试直接返回已记录的失败，不再启动付费循环。
- 实测中断后的轮次 Qoder 报告的 Credits 为 0，会话可继续使用；账户层面是否计费无法从 SDK 验证。
- 守卫只在正文出现之前生效；推理之后已开始输出的正常长回答不受影响。

## 上游等待提示

Harness 的流空闲看门狗（默认 300 秒）只把模型增量当作活动，SSE 注释心跳不算。正文开始之前，bridge 把 SDK 内部的 API 重试（含 HTTP 状态和下次重试时间）以及超过 60 秒的上游静默，以 `reasoning_content` 状态行发送。这只是 bridge 状态，不是模型输出，用于避免上游排队或重试期间被误断开。

## 在 Harness 中调节推理等级与上下文窗口

`scripts/configure-dsh.ts` 为 `qoderbridge` Provider 声明 6 个模型，并打开 `supportsReasoningEffort`（会先把原 Provider 配置备份到本机 `reports/`）：

| 模型 ID | 窗口 | 推理等级 |
|---|---:|---|
| `qoder-deepseek-flash` | 1M | low / high / max |
| `qoder-deepseek-flash-400k` | 400K | low / high / max |
| `qoder-deepseek-flash-200k` | 200K | low / high / max |
| `qoder-deepseek-pro` | 1M | high / max |
| `qoder-deepseek-pro-400k` | 400K | high / max |
| `qoder-deepseek-pro-200k` | 200K | high / max |

- **推理等级**在 Harness 的模型选择处切换，默认 max。所选等级以 `reasoning_effort` 随请求发送，bridge 逐请求交给 Qoder 模型策略。模型不支持的等级回退到 serve 默认值；等级计入本地重放匹配，换等级不会复用旧结果。
- **上下文窗口**通过选择对应模型切换。bridge 向 Qoder 请求相同窗口，Harness 按同一窗口计算上下文压力和自动压缩。DeepSeek 不按上下文长度分档计价；较小窗口让 Harness 更早压缩，减少长任务每步重复读取的命中输入，代价是压缩前的细节被摘要。
- 原有 1M 模型 ID 不变，已有会话无需改动。

多次尝试（纠错或守卫重试）的请求，发给 Harness 的 usage 为**最后一次尝试的输入（真实上下文）+ 全部尝试的输出**，避免 Harness 把累计输入当成上下文长度而提前压缩；日志的 `normalized_usage` 仍保留累计值。
